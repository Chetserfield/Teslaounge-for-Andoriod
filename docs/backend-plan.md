# TESLounge 백엔드 구성안

2026-11-01 · 제안 단계. 계정 생성·유료 계약·서버 배포·실제 차량 연결은 하지 않았습니다.

## 권장 방향

Supabase의 PostgreSQL·Auth·Storage와 서버 함수를 중심으로 시작하는 안을 제안합니다. 게시글뿐 아니라 업체, 예약, 예약 완료 후 후기처럼 서로 연결되는 데이터가 많기 때문입니다. 이는 개발자의 제안이며 제품 확정 사항이 아닙니다.

Firebase도 Android 인증과 알림 중심으로 시작하기 좋은 대안입니다. 다만 이 앱은 예약 상태와 후기 작성 자격을 함께 검증해야 하므로 관계형 데이터베이스로 규칙을 명시하는 쪽을 우선 제안합니다. 자체 서버 구축은 운영 부담이 커 초기에는 보류합니다.

현재 앱은 Java 네이티브입니다. 서버 연결 계층을 화면에서 분리하고, 공식 문서가 안내하는 Kotlin 클라이언트 적용은 별도 모듈로 검토합니다. 전체 화면을 한 번에 다시 만들 필요는 없습니다. [Android 연동 안내](https://supabase.com/docs/guides/getting-started/quickstarts/kotlin)

## 서비스 구성

| 구성 | 역할 | 첫 연결 범위 |
| --- | --- | --- |
| Android 앱 | 화면·입력·기기 캐시 | 기존 오프라인 체험 유지, 로그인 모드 분리 |
| Auth | 사용자 세션 | 개발용 이메일 로그인 검증 후 소셜 로그인 추가 |
| PostgreSQL | 회원·게시판·업체·예약 | 행 단위 접근 규칙 적용 |
| Storage | 게시글 사진·업체 이미지 | 파일 크기·형식 제한, 등록증은 별도 검토 |
| 서버 함수 | 예약 상태 변경·외부 API | 사용자 권한 검증 및 중복 요청 방지 |
| 관리자 웹 | 신고·업체·예약 운영 | 운영자 권한으로만 접근 |

## 핵심 데이터와 접근 규칙

| 데이터 | 최소 필드 | 주요 규칙 |
| --- | --- | --- |
| profiles | user_id, nickname, group, model, region | 본인만 프로필 수정. 오너 유형과 인증 상태 분리 |
| posts / comments | id, author_id, body, created_at, status | 작성자 수정·삭제, 숨김 처리된 글은 피드에서 제외 |
| reactions | user_id, post_id | 사용자·게시글 조합 중복 금지 |
| reports / blocks | reporter_id, target_id, reason | 신고자·운영자만 신고 내용 열람 |
| providers / offerings | 업체, 서비스, 차종, 가격, 공개 상태 | 운영자가 승인한 업체만 공개 |
| bookings | user_id, provider_id, offering_id, status, request_id | 본인·해당 업체·운영자만 열람, 서버에서 상태 전이 검증 |
| reviews | booking_id, author_id, rating, body | 완료된 본인 예약만 작성, 예약당 1개 |
| news_items | source_url, title, summary, published_at, approved_at | 출처와 기준일 필수, 승인된 항목만 표시 |
| vehicle_connections | user_id, vehicle_ref, status | 본인 연결만 조회. 토큰 원문은 앱에서 조회 불가 |

앱 화면에서 버튼을 숨기는 것으로 권한 검증을 대신하지 않습니다. 데이터베이스 정책과 서버 함수에서 다시 확인합니다. 서버 관리자 키는 APK에 넣지 않습니다. [서버 함수 인증 안내](https://supabase.com/docs/guides/functions/auth)

## 예약 흐름

요청 → 업체 확인 → 확정 → 서비스 완료 → 후기 작성. 취소·거절은 별도 상태로 기록합니다. 동일 요청을 재전송해도 예약이 중복 생성되지 않도록 request_id를 사용합니다. 서비스 완료는 고객이 임의로 직접 변경할 수 없게 설계합니다. 금액·서비스명은 예약 당시 값으로 보관합니다. 초기 결제 처리는 포함하지 않습니다.

## Tesla 연결

앱 회원가입과 Tesla 연결을 분리합니다. 사용자 동의 OAuth 흐름을 사용하고, 차량 계정의 비밀번호를 앱에서 수집하지 않습니다. 서버가 토큰을 보호하고 연결 해제·토큰 만료를 처리합니다. 실제 제어는 승인·도메인·키 등록·기능 범위를 확인한 다음 단계입니다. [Tesla 인증 개요](https://developer.tesla.com/docs/fleet-api/authentication/overview), [타사 토큰 흐름](https://developer.tesla.com/docs/fleet-api/authentication/third-party-tokens)

## 진행 순서와 완료 기준

1. **현재 APK 검증:** 유형 전환, 글·댓글, 체크리스트 저장, 재실행 확인.
2. **앱 구조 정리:** 화면 코드와 저장소 분리. 오프라인 데이터와 서버 데이터를 섞지 않음.
3. **개발 백엔드 준비:** 사용자 소유 프로젝트, 리전·운영 담당자·비용 설정 확인. 실제 키는 로컬 설정이나 서버 비밀 저장소로 관리.
4. **로그인·게시판 연결:** 두 테스트 계정에서 서로의 비공개 데이터 수정이 거부되는지 검증. 로그아웃·세션 만료·통신 실패 처리.
5. **업체·예약 연결:** 요청 중복, 타인 예약 접근, 잘못된 상태 전이, 미완료 예약 후기 작성이 모두 거부되는지 검증.
6. **뉴스·주식:** 공급원과 외부 표시 권한을 확보한 데이터만 연결. 실패 시 마지막 갱신 시각과 오류 표시.
7. **Fleet API:** 실제 승인 이후 테스트 차량으로 연결·해제·만료 검증. 원격 제어 범위는 별도 결정.

현재 오프라인 예시 글은 실제 서비스에 자동 업로드하지 않습니다. 사용자 작성 글도 동의 없는 자동 이전을 하지 않습니다.

## 프로젝트 생성 전에 정할 항목

- 운영 계정과 데이터 리전
- 첫 로그인 방식 및 운영용 이메일
- 뉴스·주식 공급원과 표시 범위
- 초기 업체 등록 담당자
- Tesla 개발자 신청 계정·도메인·연동 기능 범위

이 항목들이 정해지기 전에도 APK와 오프라인 화면 검증은 진행할 수 있습니다.
